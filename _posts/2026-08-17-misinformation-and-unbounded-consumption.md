# Blog 5 — Misinformation & Unbounded Consumption

> *Part 5 of a 5-part series on testing LLM-powered applications. Covers OWASP **LLM09** (Misinformation) and **LLM10** (Unbounded Consumption).*

The final two classes are the odd ones out. Neither *needs* an attacker to cause damage — the model is confidently wrong, or it's asked to do more work than it should. But both turn into real incidents the moment someone points them on purpose, and both are what you'll actually get asked about when a business worries about "AI risk."

---

# LLM09 — Misinformation

Misinformation isn't really an *attack* in the injection sense. It's what happens when you **take the model's output and use it without validation or filtering.**

Recall Blog 1: the model is autocomplete. It emits the *most probable continuation*, not the *true* one. When the probable string and the true string diverge, you get a **hallucination** — a fluent, confident, entirely fabricated answer. The model has no internal "am I sure?" gate; every answer is emitted with the same tone whether it's rock-solid or invented.

The vulnerability is on the **consumer side**: a human or a downstream system trusting that output as fact.

## Real examples

- **Fake legal citations** — a lawyer submitted a brief citing prior cases as precedent to a judge. The cases were generated by ChatGPT, and most of them **did not exist.** Fluent, correctly formatted, completely fabricated — and filed in court.
- **Wrong medical/other high-stakes advice** — a model confidently recommending an incorrect medication (or dosage) is the same failure with a worse blast radius.

The common thread: the output *looked* authoritative, so a human skipped verification.

## Why it happens

- **Next-token prediction optimizes for plausibility, not truth.** A citation-shaped string is high-probability after "the relevant precedent is"; whether that citation is *real* is not something the model checks.
- **Fluency is mistaken for competence.** Well-formed prose reads as reliable, so people lower their guard.
- **No confidence signal.** The model doesn't reliably say "I'm not sure" where it matters — uncertainty and fabrication are delivered in the same confident voice.
- **It compounds with other classes.** RAG poisoning (Blog 3) *manufactures* authoritative-looking misinformation on demand; a poisoned document the model treats as ground truth is misinformation with an attacker behind it.

## LLM09 defenses

- **Human-in-the-loop for high-stakes output** — legal, medical, financial, and safety decisions must be verified by a qualified human before use.
- **Ground answers in retrieval with citations** — force the model to cite sources the user can check (and secure that RAG layer per Blog 3, or you've just automated the misinformation).
- **Constrain scope** — don't let a general model answer questions outside its verified knowledge domain; route to authoritative systems where accuracy is non-negotiable.
- **Communicate uncertainty in the UX** — label AI output as unverified; don't present it with the visual authority of a system of record.
- **Validate outputs programmatically** where you can — check that cited cases/IDs/URLs actually exist before surfacing them.

> Misinformation is fundamentally a **process** problem: the fix isn't a better model, it's never trusting model output as fact without a verification step.

# LLM10 — Unbounded Consumption

Any path that lets a request consume disproportionate resources — leading to a **Denial-of-Service** (of availability *or* of your budget).

Because you can ask a model (or the tools/code it drives) to do arbitrarily expensive work in a single prompt, an attacker can turn one cheap request into a huge amount of compute, tokens, or downstream load.

## Examples

Simple prompts that trigger runaway work:

- *"Count from 1 to 1,000,000."*
- *"Compute the factorial of a very large number"* — pushing a code-executing agent into a heavy recursion.
- *"List every prime number from 0 to 1 trillion."*

Each looks innocent, each can pin CPU, exhaust the output-token budget, or hang a tool for a very long time. Multiply by many concurrent requests and you have an outage.

## The two things being exhausted

- **Availability** — compute/memory/time is tied up serving one abusive request, degrading service for everyone else. Classic DoS.
- **Budget ("Denial of Wallet")** — LLM calls and tool executions cost money per token/operation. An attacker who can force maximum-length, maximum-effort generations (or long tool loops) runs up your bill even if the service technically stays up.

## How it compounds

- **Agent loops** — an agent that keeps calling tools can be steered (via injection) into an unbounded loop, each iteration burning tokens and API calls.
- **Recursive / amplifying tools** — a `run_query` or `execute_shell` tool asked to do expensive work multiplies one prompt into heavy backend load.
- **Long-context abuse** — stuffing the context to its maximum on every request maximizes per-request cost (and doubles as the context-stuffing injection primitive from Blog 2).

## LLM10 defenses

- **Rate limiting and quotas** — per-user/per-key request *and* token limits; the first and most important control.
- **Cap `max_tokens` and set effort/step budgets** — bound output length and, for agents, cap the number of tool-call iterations and total token spend per task/session.
- **Timeouts on tools and generations** — no single request runs unbounded; kill long recursions and hung tool calls.
- **Input-size limits** — cap prompt/context length to prevent long-context cost abuse.
- **Cost monitoring and alerting** — watch spend per user/key and alert on anomalies (defend the wallet, not just the CPU).
- **Sandbox and resource-limit code execution** — if the agent runs code, cap CPU/memory/time in the sandbox.

# Series wrap-up

Across five posts we covered the OWASP Top 10 for LLMs:

| #     | Class                            | Core idea                                                     |
| ----- | -------------------------------- | ------------------------------------------------------------- |
| LLM01 | Prompt Injection                 | No data/instruction boundary; direct + indirect.              |
| LLM02 | Sensitive Information Disclosure | The model reveals data it shouldn't.                          |
| LLM03 | Supply Chain                     | Compromise a base block; the pyramid cascades.                |
| LLM04 | Data & Model Poisoning           | The only pre-deployment attack; baked into the weights.       |
| LLM05 | Insecure Output Handling         | Model output is untrusted input at every downstream boundary. |
| LLM06 | Excessive Agency                 | Tool access = blast radius; enforce in code, not prompts.     |
| LLM07 | System Prompt Leakage            | Recon target; treat the prompt as public.                     |
| LLM08 | Vector & Embedding Weaknesses    | The retrieval layer is a second trusted input channel.        |
| LLM09 | Misinformation                   | Confident fabrication; a process/verification problem.        |
| LLM10 | Unbounded Consumption            | DoS of availability and of your wallet.                       |

## The one lesson under all of them

There is **no single defense** that solves LLM security, because the root cause — an autocomplete engine with no architectural boundary between data and instructions — is structural. Everything is **defense in depth**:

1. Never trust model output; validate at every downstream boundary.
2. Enforce authorization and limits in **code**, never in prompt prose.
3. Treat every input channel — user, RAG, tools, web — as untrusted.
4. Least privilege on everything the model can reach.
5. Keep secrets out of the prompt.
6. Human-in-the-loop for anything high-stakes or irreversible.
7. Rate-limit, budget, and monitor.

If a security argument depends on the model "understanding" something, it's fragile. If it depends on alignment or prompt text alone, it's a *statistical mitigation* — design as though it will eventually fail, because it will.

## Where to go next

The attack surface keeps growing — cross-tenant context bleed, KV-cache timing attacks, speculative-decoding leakage, and more emerge as inference infrastructure gets more shared and more optimized. The Top 10 is where you *start*, not where the field stops. Keep red-teaming.
